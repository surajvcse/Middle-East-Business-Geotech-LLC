# Middle East Business Geotech Website Blueprint

## 1. Purpose

Build a premium, technically credible and search-friendly corporate website for Middle East Business Geotech LLC. The website must help infrastructure owners, consultants, main contractors and procurement teams understand the company’s capabilities, inspect relevant project experience and initiate a qualified enquiry.

The website will use verified company information and real project photography. It must not publish unsupported claims, invented statistics, fabricated testimonials or unverified certifications.

## 2. Primary Business Goals

1. Establish the company as a specialist geotechnical engineering and construction contractor in Oman.
2. Present design-and-execution capability across slope stabilization, foundation engineering, ground improvement and underground works.
3. Convert qualified visitors into technical consultation and quotation enquiries.
4. Build an SEO-ready service and project structure that can grow without redesigning the site.
5. Make project evidence, safety commitments and technical disciplines easy to evaluate on mobile and desktop.

## 3. Target Audiences

- Government and infrastructure authorities in Oman.
- Main contractors and EPC contractors.
- Civil, structural and geotechnical consultants.
- Road, water, mining, tunnelling and industrial project teams.
- Procurement and tendering teams looking for specialist subcontractors.

## 11. Light Theme Design System

### Design direction

Modern Engineering Authority: bright, spacious, technically disciplined and grounded in real site imagery.

### Proposed palette

- Canvas: warm off-white `#F7F6F2`.
- Surface: white `#FFFFFF`.
- Primary navy: `#123455`.
- Deep navy: `#0A2239`.
- Steel blue: `#477694`.
- Safety accent: `#D96B2B`.
- Primary text: `#202830`.
- Muted text: `#5F6972`.
- Borders: `#D9DEE2`.
- Success/verified accent: `#2F6A57`.

Safety orange is reserved for primary actions and small highlights. It will not dominate backgrounds or long text.

### Typography

- Headings: a modern technical sans-serif with strong weight and compact proportions.
- Body: highly readable neutral sans-serif.
- Prefer self-hosted or privacy-conscious font delivery.
- Body size target: 17–18 px desktop and 16–17 px mobile.
- Use clear line lengths and generous section spacing.

Final font files and licensing must be confirmed during implementation. The fallback stack must remain visually strong without remote font loading.

### Layout

- Maximum content width around 1200–1280 px.
- Strong twelve-column desktop grid.
- Comfortable mobile padding.
- Alternating white and warm-stone sections.
- Large project imagery with consistent aspect ratios.
- Restrained use of subtle contour or geological-line motifs.

### Interaction

- Short, purposeful transitions.
- Respect `prefers-reduced-motion`.
- No scroll hijacking, autoplay video or decorative animation that delays content.
- Buttons, links and menus must have visible hover and keyboard-focus states.

### Platform

- Current stable Next.js release at implementation time.
- App Router.
- TypeScript.
- React Server Components by default.
- Client Components only for interactive navigation, galleries and forms.
- Static generation for core marketing pages where practical.

### Source organization

```text
website/
├── public/
│   └── images/
├── src/
│   ├── app/
│   ├── components/
│   ├── content/
│   ├── lib/
│   └── styles/
├── package.json
├── next.config.ts
└── tsconfig.json
```

### Content model

- Company information stored once and reused.
- Services stored as typed structured data.
- Projects stored as typed structured data.
- Page metadata generated from validated content.
- Source asset filenames will be replaced with descriptive production filenames.
- Original source assets remain untouched in `source-material`.

### Performance requirements

- Use the Next.js image component for responsive delivery.
- Define image dimensions to prevent layout shifts.
- Prefer modern formats for production copies.
- Keep third-party scripts minimal.
- Avoid unnecessary client-side JavaScript.
- Establish realistic Core Web Vitals checks during browser QA.

## 15. Accessibility Requirements

- Semantic landmarks and headings.
- Keyboard-accessible navigation and controls.
- Visible focus indication.
- Sufficient colour contrast.
- Meaningful alternative text for informative project images.
- Decorative imagery ignored by assistive technology.
- Form labels, inline validation and clear error summaries.
- Reduced-motion support.
- Minimum comfortable touch-target sizes.

Target conformance: WCAG 2.2 AA for the implemented scope, subject to automated and manual verification.

## 16. Privacy and Security

- No secrets or service credentials committed to source control.
- Server-side validation for any enquiry endpoint.
- Rate limiting and spam protection before public launch.
- Do not log full enquiry payloads unnecessarily.
- Upload functionality remains out of initial scope unless secure storage, file validation and retention are explicitly approved.
- Privacy policy must reflect the actual form, analytics and third-party services used.

## 20. Validation and Acceptance Criteria

### Automated checks

- Dependency installation completes without unresolved peer conflicts.
- TypeScript check passes.
- Approved lint command passes.
- Next.js production build passes.
- Sitemap and robots routes build successfully.
- No broken internal route references in structured content.

### Manual checks

- Every implemented route opened and reviewed at representative mobile and desktop widths.
- Header, navigation, buttons, cards, galleries and forms checked with keyboard controls.
- Text and imagery reviewed for clipping, overlap and poor cropping.
- Contact details checked against approved business information.
- Project images checked against the correct project records.
- Page title, description, canonical, headings and structured data reviewed per route.
- Unavailable or unperformed checks reported as unverified rather than passed.

### Acceptance standard

The website should feel like a specialist engineering company’s corporate site: credible, restrained, visually polished, technically clear, responsive and easy to extend. It must use genuine company evidence and avoid generic template language or unsupported claims.
